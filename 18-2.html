高级网页设计 I · 第 18 章 Canvas 图形与动画 —— 一张会动的电商系统全景图

全栈系统 = 前端 + 接入层 + 后端服务 + 数据 + 第三方

你在浏览器里点一下「提交订单」，请求要经过 客户端 → 网关 → 订单服务 → 库存 → 支付 → 第三方支付 → 消息队列 → 数据库 一整条链路。这张图把每一层都画在 canvas 上，三个彩色数据包动画分别演示逛商品、提交订单、发货通知三条真实链路；点击任意节点可以看它的职责说明。

01三条业务链路怎么读这张图
颜色与图上的数据包一一对应，跟着包走一遍就是一次真实业务。

逛商品（读多写少）

  1. 浏览器发起请求，先找 CDN 要静态资源
  2. 动态请求交给 网关，路由到 商品服务
  3. 商品服务先查 Redis 缓存，命中直接返回
  4. 原路返回：服务 → 网关 → 浏览器渲染页面

提交订单（钱与库存）

  1. 小程序下单 → 网关 → 订单服务 创建订单
  2. 订单服务调 库存服务 扣减，防超卖
  3. 调 支付服务 → 发起 微信支付 → 回调验签
  4. 写 消息队列 异步通知，最终落库 MySQL

发货通知（异步解耦）

  1. 订单服务把发货事件投递给 消息队列
  2. 消费方调用 物流 API 下单取件
  3. 短信服务给用户发「已发货」通知
  4. APP 端收到推送，整条链路结束
02六层职责速查表
每一层只干一类事，出问题时先定位到层，再定位到节点。
层级职责典型技术
客户端层直接和用户交互：浏览、下单、支付调起HTML/CSS/JS Vue / React 小程序
接入层静态资源加速、统一入口、负载均衡、限流鉴权CDN Nginx API 网关
业务服务层核心业务逻辑，按领域拆成独立微服务，可单独扩容Spring Boot Node.js Go
中间件层缓存热点数据、削峰填谷、全文搜索Redis RabbitMQ / Kafka Elasticsearch
数据层业务数据持久化、静态大文件存储MySQL 主从 对象存储 OSS
第三方服务不自研的能力外包出去：支付、物流、短信微信支付 支付宝 快递 100
03为什么系统要分层
四张卡片对应四个最直接的好处。
🧩

职责单一

每层只解决一类问题，改支付不影响商品页，改代码的范围可控。

📈

独立扩容

大促只加订单服务的机器，数据库和前端不用跟着动，省钱。

🛡️

故障隔离

短信服务挂了只影响通知，下单主链路照常工作（靠 MQ 解耦）。

🤝

并行开发

前端、后端、运维按层分工，通过接口约定同时开工互不阻塞。

这张图里的节点、连线、流动数据包全部由 Canvas API 绘制（fillRect / fillText / arc / lineTo / requestAnimationFrame），和 18-1 是同一套技术栈；节点数据存在 JS 数组里，加一个服务只需加一条数据。
